# 方法与标注口径

## 1. 数据来源

使用 Steam 官方 `IUserReviewsService/GetAppReviews/v1` 公开接口。AppID 为 `391540`，默认语言 `schinese`。参数及分页游标写入采集元数据。

- `filter=1`：按最新顺序分页。默认最多 1,000 条，属于近期样本。
- `--max-reviews 0`：一直采到返回空页。采集期间评论可能新增或修改，因此并非冻结的数据库快照。
- `purchase_type=1`、`review_type=0`：包含所有购买来源及正负评价。注意两组枚举的 All 值不同。
- `filter_offtopic_activity=false`：保留偏题活动期评论，便于研究社区表达。
- Steam 语言标签由平台数据提供；标为简体中文的记录仍可能含英语、字符画或数字。
- 原文保留，按 `recommendationid` 去重；不保存作者 SteamID。不同编号的同文评论保留。

不要用“最有帮助前 100 条”或“最欢乐前 100 条”估计玩家总体玩梗比例，也不要据此比较投票差异。这类样本已按研究结果变量筛选，仅适合发现模板、测试规则。

## 2. 特征与主题聚类

文本 NFKC 规范化、BBCode 标记清理、空白规范化 → jieba 分词及 UNDERTALE 词典 → TF-IDF（1–2 gram）→ K-means。默认请求 8 类；每类平均至少约 3 条独立文本的规模限制会自动减小类数。

至少有两个有效词元的文本参与建模。其余标为 `-1`，表示信息不足，不表示无价值。归一化后相同的文本只拟合一次，再将主题映射回全部评论，避免复制模板压倒聚类结果。原始同文频次仍保留用于社区现象研究。

主题标签只使用文本，不使用投票、推荐状态和游玩时长。关键词与距离中心最近的三条独立评论帮助人工命名主题。编号没有跨实验语义；改变样本或参数后不可直接比较“主题 0”。

固定随机种子 42，记录输入哈希、词典/规则哈希、参数和依赖版本。余弦轮廓系数仅供诊断，不等于主题的人工可解释性。SVD 二维散点只作浏览，不代表真实类别边界。

## 3. 玩梗候选与人工标注

玩梗类型独立于主题，一条评论可同时评价剧情并引用台词。规则命中只是候选；未命中规则不等于非玩梗。候选类型包括台词化表达、角色模仿、反讽句式、求赞模板和字符画。

以下信号不能单独作为玩梗标签：短、重复、角色名字、好评、欢乐票多、玩了很久。中文/汉化诉求另存为 `localization_request`，不自动算玩梗。

在 `annotation_blind.csv` 填写：

| label | 含义 |
|---|---|
| `meme` | 有明确的引用、模仿、反讽、模板等幽默或圈内表达意图 |
| `non_meme` | 普通评价、信息诉求等，无足够玩梗证据 |
| `uncertain` | 需要上下文或无法判断 |
| 空白 | 尚未标注 |

`meme_type` 填细分类别，`notes` 写理由。严肃引用台词可能不是玩梗，需看语境。表格不显示投票、模型预测和游玩时长，降低提示偏差。

相同规范化文本按哈希进入同一 `dev` 或 `test` 组，比例约 80/20（小样本不保证精确比例）。只根据 dev 修改规则；规则冻结后再看 test。若近似模板仅更改少量文字，应人工合并组以避免泄漏。本项目不自动解决近重复语义泄漏。

建议先随机抽取一批样本，再补充少见类型；用于总体效果评估的测试集应保留随机抽样组成。若有第二位标注者，可对部分样本独立复核并记录分歧。本项目只有人工标签文件存在时才计算 Precision、Recall、F1；不把示例数据测得的指标写成真实玩家数据结果。

## 4. 投票关联

输出每个主题 × 候选组的样本量、累计有帮助/欢乐票的均值、中位数和零票比例。另外按评论年龄（≤30 天、31–365 天、>365 天）与长度（≤20、21–100、>100 字符）分层。

均值容易被少数热门评论影响，要一起看中位数、零票比例、组内样本量。年龄和长度分层只能缓解部分混杂；没有曝光量、阅读次数，不能解释成“获得投票的概率”或“玩梗导致投票增加”。跨时间采集要记录采集时刻，不能将不同暴露时长当成相同条件。

## 5. 本版本的边界

中文词典与规则是可审计的基线，尚无人工标注测试集的真实准确率。纯 TF-IDF 聚类可能受角色名、英语和复制模板影响。当前报告提供描述性统计，不包含回归因果推断或自动生成课程结论。

完成真实采集与标注后，再依据结果选择要写入两页 PPT 与报告的发现。课程作品中的自有工作应具体注明：样本设计、词典与规则修订、标注、错误分析和可视化。
